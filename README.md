# SORTHOUSE

**Human-in-the-loop AI triage for email and documents.** Classification, schema-validated extraction with field-level evidence, confidence gating, an approval queue, reply drafts and idempotent safe actions.

Demo: https://sorthouse.syslora.com (noindex, synthetic data). This is a portfolio lab, not a production product.

The question it answers is not "can an LLM say this is an invoice?" but: can the system decide when it has enough evidence to automate, send uncertain cases to a person, keep the provenance of every field, and never run an action twice when jobs, webhooks or providers fail?

## Hero flow (about two minutes)

1. `Launch demo` starts an isolated session with a synthetic inbox: invoices (text PDF, photographed), a complaint, a request for quote, spam/phishing, a general question, an ambiguous message.
2. Each message goes `received -> sanitized -> classified -> attachments -> extracted -> validated -> policy checked -> review/ready`. The stepper shows measured stage times.
3. Open the clear PDF invoice: fields, schema validation and evidence for every value. Open the photographed one: the simulated OCR confuses `0/O`, `8/B`, `1/l`; the field is flagged and the evidence region is drawn on the image.
4. `Correct` a field: the original prediction stays in the audit, validation and policy run again.
5. `Approve` the complaint: `approved -> queued -> executed (SIMULATED)` through a transactional outbox. The reply draft is never sent.
6. `Failure Lab`: prompt injection (blocked, zero tool escalation), duplicate delivery x3 (one case), concurrent reviewers (one wins, one gets a version conflict), timeout after send (reconciled, not re-sent), LLM/OCR timeouts, invalid JSON, 429, worker crash.
7. `Evaluation`: measured numbers with the dataset size and the provider label.

## What is LIVE and what is SIMULATED

| Part | Status |
|---|---|
| Inbox, invoices, photos, OCR output | **Simulated**: a deterministic synthetic corpus generated by `php artisan fixtures:build`. No real data. |
| Classifier / extractor | **Simulated by default**: a deterministic heuristic baseline (regex and keyword rules, not an LLM). OpenAI, Anthropic and Gemini adapters exist behind the same interfaces and activate only from server-side config. They are covered by HTTP-fake tests; **they have not been run against the live APIs** in this repository. |
| OCR, malware scan, mail provider, action execution | **Simulated** (labelled in the UI). Gates and idempotency behave as they would in production. |
| State machine, outbox, optimistic locking, policy, validation, evidence, audit, queue (Redis/Horizon), PostgreSQL | **Live** and tested, including parallel-process tests. |

Badges `LIVE`, `SIMULATED`, `FALLBACK`, `BLOCKED` appear wherever they apply.

## Architecture in one picture

```
mail fixture -> Ingest (dedupe, sanitize, MIME sniff, scan) -> TriagePipeline (queued, resumable)
   classify -> extract -> normalize -> resolve evidence -> validate -> confidence -> ActionPolicy
        AUTO_ELIGIBLE -> approval by policy -> outbox        REVIEW_REQUIRED -> Approval Queue
        BLOCKED -> no action possible                              | Approve / Correct / Reject
Approve -> action_request + outbox_message (one transaction) -> worker -> executor (SIMULATED) -> reconcile on unknown outcome
```

Laravel 13 / PHP 8.4 modular monolith (`app/Domain`, `app/Application`, `app/Infrastructure`, `app/Http`), PostgreSQL 17, Redis + Horizon, Alpine UI. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Safety model

Three different things are never confused: **model signal** (what a provider reports), **validation** (deterministic checks: JSON Schema, types, totals, dates, currency, evidence availability) and **automation policy** (the business rule that decides what may run). A perfectly valid JSON is not proof that the data is right; a high model signal does not make an action safe. `ActionPolicy` is the mandatory boundary between interpretation and any effect. Details in [docs/SECURITY.md](docs/SECURITY.md).

## Measured results

On the included synthetic corpus, with the SIMULATED heuristic baseline and policy `policy.v1` (`auto_min` 0.85), full detail in [docs/EVALUATION.md](docs/EVALUATION.md):

| Run | Cases | Macro F1 | Invoice critical-field accuracy | Auto coverage | Precision of auto | False auto actions | Unsafe blocked |
|---|---|---|---|---|---|---|---|
| Dev (tuning) | 76 | 89.6% | 95.1% (82 cells) | 15.8% | 100% (12) | 0 | 16/16 |
| **Held-out** | 122 | 80.0% | 93.1% (144 cells) | 16.4% | 100% (20) | 0 | 16/16 |

The held-out run includes 100 held-out emails plus 22 adversarial and failure fixtures. Photographed and scanned invoices are read with deliberate misreads, so their documents are only exact after a human correction (PDF 100%, photo 0%, scan 0% before review), which is the point of the review step. These numbers describe this synthetic lab, not any real inbox, and a rules engine will not generalise. Real-model runs are stored separately with their own provider label.

## Run it

```bash
cp .env.example .env && composer install && php artisan key:generate
docker compose up -d db redis
php artisan migrate --seed
npm ci && npm run build
php artisan serve &
php artisan queue:work redis &         # or: php artisan horizon
```

Full stack in containers: `docker compose --profile app up -d --build` then http://127.0.0.1:8139.

Real providers (server-side only, never in the browser): set `AI_PROVIDER=openai|anthropic|gemini` and the matching `*_API_KEY` and `*_MODEL` in `.env`; check the provider's current models, structured-output guarantees, retention terms and prices first. Without keys the app uses the baseline and says so.

Useful commands: `php artisan eval:run holdout`, `php artisan policy:simulate`, `php artisan fixtures:build`, `php artisan demo:purge`.

## Limitations (read these)

- The default engine is a rules baseline. Its F1 says nothing about an LLM, and LLM confidence is not a calibrated probability anywhere in this project.
- OCR is simulated; real photographs will fail on blur, perspective, handwriting and unusual layouts.
- Prompt injection is mitigated in layers (delimited prompts, no tool freedom, server-owned recipients, allow-listed actions, a deterministic detector); it is not solved.
- Evidence on real vision output would be page-level unless the OCR engine returns stable boxes; the UI states this.
- Spam/phishing classification is a demonstration, not a security product.
- The synthetic corpus is easier than a real inbox. 122 evaluated cases are enough to be understood, not to prove anything about production.
- Not production-ready: backup restore, monitoring, incident flow and a full permission model are not validated.
